### Задание. Необходимо определить требуемые ресурсы
Известно, что проекту нужны база данных, система кеширования, а само приложение состоит из бекенда и фронтенда. Опишите, какие ресурсы нужны, если известно:

1. Необходимо упаковать приложение в чарт для деплоя в разные окружения. 
2. База данных должна быть отказоустойчивой. Потребляет 4 ГБ ОЗУ в работе, 1 ядро. 3 копии. 
3. Кеш должен быть отказоустойчивый. Потребляет 4 ГБ ОЗУ в работе, 1 ядро. 3 копии. 
4. Фронтенд обрабатывает внешние запросы быстро, отдавая статику. Потребляет не более 50 МБ ОЗУ на каждый экземпляр, 0.2 ядра. 5 копий. 
5. Бекенд потребляет 600 МБ ОЗУ и по 1 ядру на копию. 10 копий.

----

### Правила приёма работы

1. Домашняя работа оформляется в своем Git-репозитории в файле README.md. Выполненное домашнее задание пришлите ссылкой на .md-файл в вашем репозитории.
2. Сначала сделайте расчёт всех необходимых ресурсов.
3. Затем прикиньте количество рабочих нод, которые справятся с такой нагрузкой.
4. Добавьте к полученным цифрам запас, который учитывает выход из строя как минимум одной ноды. 
5. Добавьте служебные ресурсы к нодам. Помните, что для разных типов нод требовния к ресурсам разные. 
6. В результате должно быть указано количество нод и их параметры.

# Выполнение домашнего задания

## 1. Суммарные ресурсы приложений

| Компонент | Копий | RAM на копию | CPU на копию | RAM всего | CPU всего |
|-----------|-------|--------------|--------------|-----------|-----------|
| БД        |     3 |         4 ГБ |            1 |     12 ГБ |         3 |
| Кеш       |     3 |         4 ГБ |            1 |     12 ГБ |         3 |
| Фронтенд  |     5 |        50 МБ |          0,2 |   0,25 ГБ |         1 |
| Бекенд    |    10 |       600 МБ |            1 |      6 ГБ |        10 |
| Итого     |       |              |              |   ~ 30 ГБ |   17 vCPU |

## 2. Количество нод

БД и кеш - отказоустойчивые, по 3 копии. Их нельзя ставить на одну ноду: если нода упадёт, потеряем сразу несколько копий. Значит, минимум 3 ноды.  

Плюс по заданию нужен запас на отказ одной ноды  

Получается 4 worker-ноды  

## 3. Поды по нодам

* БД: по 1 копии на первые 3 ноды
* Кеш: по 1 копии на первые 3 ноды
* Бекенд (10 копий) и фронтенд (5 копий) - примерно поровну

| Нода     | БД | Кеш | Бекенд | Фронтенд | RAM    | CPU |
|----------|----|-----|--------|----------|--------|-----|
| worker-1 |  1 |   1 |      3 |        2 | ~10 ГБ |  ~5 |
| worker-2 |  1 |   1 |      3 |        2 | ~10 ГБ |  ~5 |
| worker-3 |  1 |   1 |      2 |        1 |  ~9 ГБ |  ~4 |
| worker-4 |  - |   - |      2 |        - |  ~2 ГБ |  ~2 |

Самая загруженная нода ~10 ГБ и ~5 vCPU.

## 4. Запас на отказ ноды (N+1)
Если упадёт самая загруженная нода (worker-1: ~10 ГБ / 5 vCPU), её нагрузка распределится по трём оставшимся 3 примерно по 3,3 ГБ и 1,7 vCPU на каждую.

У оставшихся нод есть свободные ~6 ГБ RAM и ~2,5 vCPU - хватает.

Кворум БД/кеша сохраняется - 2 копии из 3 живы.

## 5. Служебные ресурсы

* Worker-нода - на каждой из 4 нод живут ОС, kubelet, kube-proxy, containerd, DaemonSet'ы мониторинга (_~2 ГБ RAM и ~1 vCPU на ноду_).

* Control plane-нода - apiserver, etcd, scheduler, controller-manager, ОС (_~2 ГБ RAM и ~1,5 vCPU_).

Количество control plane-нод - 1.  
Три управляющие ноды с кворумом etcd нужны в крупных продакшн-кластерах, где отказ управления критичен. Для проекта с 4 worker это избыточно и дорого: кластер нормально управляется с одной control plane-нодой.  
На случай сбоя есть бэкап etcd.

## 6. Результат

| Роль      | Кол-во | Параметры                         |
|-----------|--------|-----------------------------------|
| Control   |      1 | 1,5 vCPU /  2 ГБ RAM / SSD 50 ГБ  |
| Worker    |      4 | 8   vCPU / 16 ГБ RAM / SSD 200 ГБ |
| Всего нод |      5 |                                   |

Параметры подобраны с запасом на отказ одной ноды:
- RAM worker-пула: 4 * 16 = 64 ГБ. Служебка на 4 worker (~8 ГБ) - остаётся ~56 ГБ при потребности ~30 ГБ. Запас ~1,9x.
- CPU worker-пула: 4 * 8 = 32 vCPU. Служебка (~4 vCPU) - остаётся ~28 при потребности 17. Запас ~1,6x.
- 8 vCPU / 16 ГБ - удобный круглый размер, в который с запасом влезает ~10 ГБ / ~5 vCPU нагрузки на самой загруженной ноде.
- Control plane - 1 нода минимального размера (2 ГБ / 1,5 vCPU), потому что отказоустойчивость управления для данного проекта избыточна.
